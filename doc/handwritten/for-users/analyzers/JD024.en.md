# JD024: ConstraintWithNoEffect

🌍 **Languages:**  
🇬🇧 English (this file) | 🇫🇷 [Français](./JD024.fr.md)

| Property | Value |
|---|---|
| **Category** | Constraints (`JustDummies.Constraints`) |
| **Severity** | 🔵 Info |
| **Enabled by default** | Yes |

The constraint is legal and **inert**: the domain it produces is the one that already existed.

This is the only member of the constraint family the run time **never** reports. Every other contradiction throws eventually and loudly; an inert constraint leaves the test green while it exercises a domain the author did not write.

The dangerous case is an exclusion of a sentinel the generator could never draw. It silently misses — and starts mattering the day someone widens the range, at which point the sentinel begins appearing and a distant test starts failing on it.

## Noncompliant

```csharp
Any.Int32().Between(1, 10).Except(20)      // JD024: 20 was never in [1, 10]
Any.Int32().Positive().GreaterThan(-5)     // JD024: Positive() already requires ≥ 1
Any.String().Except()                      // JD024: an empty exclusion removes no value
```

## Compliant

```csharp
Any.Int32().Between(1, 30).Except(20)      // the exclusion now removes something
Any.Int32().Positive().GreaterThan(100)    // the bound now narrows
```

## An exclusion written empty

`Except()`, `Except([])`, `Except(new T[0])` and `Except(Array.Empty<T>())` exclude nothing, on every generator: the run time accepts them as a no-op ([ADR-0122](../../for-maintainers/adr/0122-accept-an-empty-exclusion-as-the-identity.md)), and this rule reports them wherever the list is written empty. A list computed at run time is not reported, even when it turns out empty — a set of values already used that starts empty is exactly what the no-op is for.

## Info rather than Warning

A defensive or documentary constraint is a real and reasonable style: a team writes `.Except(0)` on a range that already excludes 0 so the intent survives a future widening. The rule states the fact without insisting it is a defect.

## What it does not flag

* An exclusion that removes at least one reachable value.
* A bound that genuinely narrows the domain.
* **The same bound declared twice** — `GreaterThanOrEqualTo(10).GreaterThanOrEqualTo(8)`. That is one phenomenon in both writing orders and in every generator family, so it has a rule of its own: [JD032](JD032.en.md), at warning severity. This rule keeps a bound implied by a *different* one, which is the shape its examples above show.
* **The same exclusion written twice** — `Except(5).Except(5)`. That is a repetition, which [JD035](JD035.en.md) reports at warning severity in every generator family. This rule keeps an exclusion made inert by a *different* one, such as `Except(5).DifferentFrom(5)`.
* Anything on a non-integer generator but an exclusion written empty, or a chain with a non-constant argument.
* A `UInt64` argument above `long.MaxValue` — the model reasons in `long`, so the chain is left alone rather than judged on a truncated value.
