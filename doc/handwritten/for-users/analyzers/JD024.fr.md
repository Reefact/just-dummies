# JD024 : ConstraintWithNoEffect

🌍 **Langues :**  
🇫🇷 Français (ce fichier) | 🇬🇧 [English](./JD024.en.md)

| Propriété | Valeur |
|---|---|
| **Catégorie** | Contraintes (`JustDummies.Constraints`) |
| **Sévérité** | 🔵 Info |
| **Activée par défaut** | Oui |

La contrainte est légale et **inerte** : le domaine qu'elle produit est celui qui existait déjà.

C'est le seul membre de la famille des contraintes que l'exécution ne signale **jamais**. Toutes les autres contradictions finissent par lever, bruyamment ; une contrainte inerte laisse le test au vert alors qu'il exerce un domaine que l'auteur n'a pas écrit.

Le cas dangereux est l'exclusion d'une valeur sentinelle que le générateur n'aurait jamais pu tirer. Elle manque sa cible en silence — et se met à compter le jour où quelqu'un élargit la plage, moment où la sentinelle commence à apparaître et où un test lointain se met à échouer sur elle.

## Non conforme

```csharp
Any.Int32().Between(1, 10).Except(20)      // JD024 : 20 n'a jamais été dans [1, 10]
Any.Int32().Positive().GreaterThan(-5)     // JD024 : Positive() exige déjà ≥ 1
Any.String().Except()                      // JD024 : une exclusion vide ne retire aucune valeur
```

## Conforme

```csharp
Any.Int32().Between(1, 30).Except(20)      // l'exclusion retire maintenant quelque chose
Any.Int32().Positive().GreaterThan(100)    // la borne rétrécit maintenant
```

## Une exclusion écrite vide

`Except()`, `Except([])`, `Except(new T[0])` et `Except(Array.Empty<T>())` n'excluent rien, sur tout générateur : l'exécution les accepte comme une opération neutre ([ADR-0122](../../for-maintainers/adr/0122-accept-an-empty-exclusion-as-the-identity.fr.md)), et cette règle les signale partout où la liste est écrite vide. Une liste calculée à l'exécution n'est pas signalée, même quand elle se révèle vide — un ensemble de valeurs déjà utilisées qui commence vide est précisément ce pour quoi l'opération neutre existe.

## Info plutôt qu'avertissement

Une contrainte défensive ou documentaire est un style réel et raisonnable : une équipe écrit `.Except(0)` sur une plage qui exclut déjà 0 pour que l'intention survive à un élargissement futur. La règle énonce le fait sans prétendre qu'il s'agit d'un défaut.

## Ce qui n'est pas signalé

* Une exclusion qui retire au moins une valeur atteignable.
* Une borne qui rétrécit réellement le domaine.
* **La même borne déclarée deux fois** — `GreaterThanOrEqualTo(10).GreaterThanOrEqualTo(8)`. C'est un seul phénomène dans les deux ordres d'écriture et dans toutes les familles de générateurs, il a donc une règle à lui : [JD032](JD032.fr.md), en sévérité avertissement. Cette règle-ci garde une borne impliquée par une *autre*, qui est la forme que montrent ses exemples ci-dessus.
* **La même exclusion écrite deux fois** — `Except(5).Except(5)`. C'est une répétition, que [JD035](JD035.fr.md) signale en sévérité avertissement dans toutes les familles de générateurs. Cette règle-ci garde une exclusion rendue inerte par une *autre*, comme `Except(5).DifferentFrom(5)`.
* Quoi que ce soit sur un générateur non entier hormis une exclusion écrite vide, ou une chaîne avec un argument non constant.
* Un argument `UInt64` au-delà de `long.MaxValue` — le modèle raisonne en `long`, la chaîne est donc laissée tranquille plutôt que jugée sur une valeur tronquée.
