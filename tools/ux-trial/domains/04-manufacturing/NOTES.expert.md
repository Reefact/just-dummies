## Frictions and surprises, in order
1. **`dotnet test --project Tests.Expert` does not work out of the box on the .NET 10 SDK.** First `dotnet test --project Tests.Expert` -> `MSBUILD : error MSB1001: Unknown switch.` (VSTest mode). `dotnet test Tests.Expert` -> `Microsoft.Testing.Platform.MSBuild.targets(395,5): error : Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later. If you use dotnet test, you should opt-in to the new dotnet test experience`. I had to guess the fix (a `global.json` with `"test": { "runner": "Microsoft.Testing.Platform" }`, which I put in W). Nothing in the user docs (`justdummies-xunit.en.md`, getting-started) mentions that xunit.v3 4.0.2 + SDK 10 needs this, nor that the project must be `OutputType Exe`. Expected: a one-line prerequisite on the xunit page.
2. **Scaffolded types land in the domain's namespace** (`namespace Manufacturing.Domain;`), so test-only generators sit in the production namespace and `Any.Machine()` extensions appear on `Any` for anyone importing `Manufacturing.Domain`. The output said `in namespace Manufacturing.Domain (--namespace to change).` — informative, but the default is the opposite of what a test project wants; I kept it (it makes the types reachable with no `using`) and noted it. Expected default: the test project's root namespace, or at least a line in the CLI page's "Run it from your test project" section.
3. **Four of seven scaffolds do not compile until hand-completed, and three of the four are because of `Validate(...)`/static-readonly constants, not exotic guards.** `Tolerance` -> `nominalMm: unread guard at Tolerance.cs, line 7: Validate(nominalMm, minusMm, plusMm);` x3 (a `void` private helper, as the docs say is "marked as before"); `CycleTime` -> `if (duration < Shortest)` not read because `Shortest` is a `static readonly TimeSpan`, not a constant, `... and 2 more`; `Machine` -> regex and a `switch` expression. All documented, all honest, all correct to block. But the recap gives no hint of *how* to write the replacement for the tie rules (Tolerance: `minus < nominal`, `minus + plus != 0`); I wrote bands by construction. The "When a guard ties two parameters" section was the page that helped.
4. **`ShiftWindow`: the tool read half of the tie and then stopped.** Recap: `start: unread guard at ShiftWindow.cs, line 12: if (end - start > LongestShift) { ... — ties end to start`. It had scaffolded an `AnyOrderedPair<DateTime>` for `start >= end` (good), yet the two `TODO(any): verify` lines remain and the generated `WithStart`/`WithEnd` pin API cannot carry the second guard. The docs' advice ("draw a start and a duration") means throwing the pair away and restructuring the file, which I did by rewriting it (`WithStart`/`WithLength`). The `--force` warning in the docs is relevant: the next `any generate ShiftWindow --force` would silently destroy this. Idea: when one of two ties is an order, offer the start+duration shape as the scaffold.
5. **The generated `WithXxx(Func<AnyX, AnyX>)` is the nicest part, but a lambda cannot reach into a hand-rewritten generator unless I write both overloads myself.** `Any.WorkOrder().WithWindow(w => w.WithLength(TimeSpan.FromHours(8)))` reads very well and `FitsInWindow` tests are clear; but the hand-written `AnyShiftWindow` only supports it because I copied the pin/lambda pair by hand from the scaffold. No friction beyond the copy.
6. **Pinning `null` to test a null guard needs a cast and an `!`**: `Any.WorkOrder().WithCadence((Cadence)null!)` (without the cast it is ambiguous between the pin and the lambda overload). Worked as documented (`Any.Fixed(null)` accepted), but the idiom is noisy in four near-identical tests.
7. **`[Reproducible]` prints its seed also for tests that draw nothing.** My `The_largest_quantity_does_not_overflow_the_computation` has no `Any.*` call and its failure still said `[JustDummies] These arbitrary values were seeded with 776935328. Reproduce this run with [JustDummies.Xunit.Reproducible(Seed = 776935328)].` With `[assembly: Reproducible]` this appears on every failure, including the ones that cannot depend on a seed (my own arithmetic slip, a lambda-ordering slip); a reader may chase a replay that cannot change anything. Low severity; wording only.
8. **Where is a dummy, really, in a value-object test?** Strictly applying the "the value the assertion is about is not a dummy" rule left `Cadence`, `CycleTime`, `Tolerance`, `BatchCode` equality and boundaries almost entirely literal (correct, and I deliberately did not draw `Between(...)` inputs for them: that would be a one-sample property). The dummies appear where something is irrelevant: the year/sequence of a batch code when testing plant/week, a whole `WorkOrder` when testing `RecordPart`, a machine id, a window start when only the length matters. The docs say this clearly; I record it because the first draft of several tests wanted `anyCadence` in the assertion, which the docs' rule correctly rejected.
9. **JD030 on a scaffolded row is Info and invisible**; I only found it by raising all JD0xx to `warning` through an `.editorconfig` (the docs say how). The single hit was the scaffolded `Any.ListOf(Any.String())` for `operators` (`AnyWorkOrder.cs(70,27): warning JD030: This string dummy declares no length: it draws 0 to 1024 characters`). The domain says operator names are not validated, so the right fix was to *state* the widest length (`WithLengthBetween(0, 1_024)`) and a count (`WithCountBetween(1, 5)`), with a comment. No other rule fired on 124 tests, which is itself reassuring.
10. **`WithGranularity` on `Between(1s, 1h)` for a `TimeSpan`, and the same on `DateTime`, behaved as documented** (500 draws of each generator construct; see `GeneratorsTests`). No friction; listed because the docs promised a "grid" without saying where its origin is, and I relied on it landing on the whole seconds starting at zero. It did here; a `Between(1.5s, ...)` case is not covered by what I read.
11. **Domain observations (not library):** five tests are skipped as domain defects, each confirmed by un-skipping: `BatchCode` and `Machine` ids accept a trailing line break (`$` matches before a final `\n`: `new BatchCode("LYN-2614-0042\n")`, `new Machine("M-123\n", …)`), `Machine` id accepts non-ASCII digits (`\d`, e.g. `M-١٢٣`), `WorkOrder` with a null operator list and `RecordPart(null, …)` throw `NullReferenceException` rather than `ArgumentNullException` while every other argument is guarded. The two NRE cases are listed as such in MODEL.md, so they are a design observation more than a surprise.

## What worked well
- The `any` recap is honest and actionable: `Cadence` and `WorkOrder` (composed of `new AnyBatchCode()`, `new AnyCadence()`, ...) came out right with no edit, `guard` rows referencing `Cadence.MaximumUnitsPerHour` instead of copying `10000` is exactly what I would have asked for, and the `Machine` ambiguity note (`Machine resolved to Manufacturing.Domain.Machine; System.Reflection.PortableExecutable.Machine also answers to that name.`) pre-empted a confusion.
- Failing the build on a `TODO` I have to read is the right trade: the five hand-completed recipes are the five places where the domain has a real rule, and I read each constructor because of it.
- The `With…(lambda)` refine-the-valid-base idiom makes the arrange block say only what matters: `Any.WorkOrder().WithPlannedQuantity(480).WithCadence(new Cadence(60)).WithWindow(w => w.WithLength(TimeSpan.FromHours(8)))` — the pinned values are exactly the assertion's inputs, everything else stays drawn.
- `Any.StringMatching` on a pattern that I copied nearly verbatim from the domain's regex (`(0[1-9]|[1-4][0-9]|5[0-3])` for the week) worked first time, and `[0-9]{2}` drawn year/sequence in the batch-code tests make visible that those parts are irrelevant to plant/week.
- `[assembly: Reproducible]` plus the seed in failure output: the two failures I caused came with a replay line and cost nothing in silence when green. 12 reruns, 266 cases each, zero flakiness; the generators survive 500 draws each.
- Compile-time guidance was enough everywhere: not once did I have to look at anything but the docs and the tool output.

## Fluency: 4 / 5
Once the SDK 10 / Microsoft.Testing.Platform runner opt-in was understood (undocumented, friction 1) the library itself got out of the way: the generators, `With…` lambdas, pattern generation and `[Reproducible]` composed without surprises, and the analyzers stayed silent on 124 tests. The score is held down by the cost of the five generators the tool could not finish (every cross-parameter rule in this domain is one of them, and `ShiftWindow` had to be rewritten rather than completed), and by a default namespace and an Info-level JD030 that both need knowing about in advance.
