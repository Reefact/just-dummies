## Frictions and surprises, in order
1. `dotnet test --project Tests.Regular` (the command given in the brief) does not run on SDK 10.0.114 out of the box.
   Output: `MSBUILD : error MSB1001: Unknown switch. ... --project Tests.Regular`. Plain `dotnet test Tests.Regular` then says
   `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later. ... opt-in to the new dotnet test experience`.
   I expected `--project` to work. I added `global.json` at the workspace root with `{"test": {"runner": "Microsoft.Testing.Platform"}}`, after which both `--project` and the result summary worked. This is an SDK matter, not a library one, but the docs (`dotnet test --solution`) assume the opt-in and never say so; the first error message (MSB1001) is the misleading one.
2. `any generate` before any restore: `✗ BatchCode: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. Clear and actionable; one extra step.
3. `ShiftWindow` (`end - start > 12 h`): the tool recognised a tie, emitted `Any.OrderedPair(..., strict: true)` and marked both parameters `to verify, guard, unread guards` ("ties end to start"). The scaffolded pair can never honour a "difference at most N" rule, and the documented cure ("draw a start and a duration") means leaving the scaffolded structure: I rewrote the file (~80 lines, new `WithLength`, no more `WithEnd(Func)`). The `guard` tag on a row that is entirely unread is also confusing. I would have liked a scaffold hint for the `end - start > X` shape (start + `Any.TimeSpan()` bounded by X), or at least that the TODO text suggest it.
4. `Tolerance`: the guards live in a `private static void Validate(a, b, c)` called from the constructor, so all three parameters came out as bare `Any.Decimal()` with `to verify, unread guards` and the same comment (`Validate(nominalMm, minusMm, plusMm);`) three times. Nothing says which of the checks is the one that matters for which parameter. I read `Validate` myself and picked narrow ranges (minus <= 0.9, nominal >= 1) so that `minus < nominal` always holds; the price is that nominal values below 1 mm are never drawn. Expected (and accepted): the tool cannot read a void helper; the cost is variety in the dummy.
5. `BatchCode`: the regex lives in a `static readonly Regex` and the guard is `if (!match.Success)`, so the tool's comment only says `verify against BatchCode.cs, line 13: if (!match.Success) { ...` with no pattern and no hint to use `Any.StringMatching` (the Machine comment, where the regex is inline, did say it and told me which four places to retype). I knew from the strings page what to do, but a first-time reader gets a vaguer comment for the same situation.
6. The retype `AnyString` -> `AnyPattern` (BatchCode, Machine) was mechanical as announced; a global replace on the file did it in one go (every `AnyString` in those files is the one to change). Fine, but it is a manual edit of generated code each time a regex guard is met.
7. The tool printed `Machine resolved to Manufacturing.Domain.Machine; System.Reflection.PortableExecutable.Machine also answers to that name.` Good to know it took the right one; no action.
8. Scaffolded files live in the domain's own namespace (`Manufacturing.Domain`) even though they are in the test project; harmless, `--namespace` exists, but my tests need no extra `using` beyond the domain's. Noted only because it looks odd in a test project.
9. Surprise from the domain, not the library: drawing a `ShiftWindow` start from `Any.DateTime().Between(...)` gives `Kind = Utc`, whereas my literal windows are `Unspecified`; no test is affected since `ShiftWindow` does not check `Kind` (documented), I only checked it explicitly in one test.
10. The draws did not reveal anything by themselves in this suite (no red on a drawn value in 13 runs); the six domain defects came from edge cases a reviewer would think of (trailing newline with `$`, `\d`, a null argument, int.MaxValue), not from the seeds.

## What worked well
- The scaffold read the simple guards perfectly: `Cadence` (with the constant `Cadence.MaximumUnitsPerHour` referenced rather than copied) and `WorkOrder` (sku `NonEmpty().WithMaxLength(20)`, quantity `Positive().LessThanOrEqualTo(100000)`, operators `NonEmpty()`, nested `new AnyBatchCode()` etc.) needed no change at all.
- The build-stopping sentinel is the right design: every unread guard stopped me at the line, and the comment text told me where to look.
- `Any.StringMatching` with a group alternation (`(0[1-9]|[1-4][0-9]|5[0-3])`) reproduced the week rule exactly; `DifferentFrom` on a typed builder and on a pattern made the "not equal" tests one line.
- `.OneOf(...)` on `Any.Enum<MachineState>()` for the allowed initial states; `With…(value)` pins made the state-machine helper (`MachineIn(state)`) trivial.
- `[assembly: Reproducible]` is a single line and leaves the test bodies untouched; no analyzer noise at all on 107 tests.
- Messages on contradictory constraints were never needed, which is itself a sign the DSL read naturally.

## Fluency: 4 / 5
The day-to-day DSL and the scaffold were fast; almost everything compiled and went green at the first run, and the generators for the two guard-heavy types (BatchCode, Machine, CycleTime) took minutes. Points lost for the time spent on `ShiftWindow` (the scaffold's ordered pair cannot express a bounded difference, so I rewrote the generator by hand), for `Tolerance` (a void `Validate` helper leaves three untyped TODOs and a hand-derived relation between them), and for the `dotnet test --project` setup surprise, which is an SDK matter but stalled the first run.
