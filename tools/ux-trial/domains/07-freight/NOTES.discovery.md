## Frictions and surprises, in order
1. **`dotnet test --project Tests.Discovery` does not work out of the box.** Output: `MSBUILD : error MSB1001: Unknown switch.` ... `Switch: --project`. On the .NET 10 SDK, `--project` is a Microsoft.Testing.Platform (MTP) switch of the new `dotnet test`; it needs `global.json` with `"test": { "runner": "Microsoft.Testing.Platform" }`. Neither the xUnit adapter page nor getting-started says that a test project (template: `OutputType Exe`, `xunit.v3`) must be run that way; the only test commands shown are in the project README's *Contributing* section (`dotnet test --solution ...`), which concern the library's own repo. I expected a one-liner in the xunit page. I added a `global.json` next to the `Domain/` folder (inside my workspace) and it worked.
2. **`any generate` before `dotnet restore`**: `✗ UnLocode: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. The message is clear and actionable (good), but the docs' "What it produces" says only "Run it from your test project" and never mentions restoring first; a newcomer who follows the page literally hits this on the first command.
3. **Every value object with a regex guard becomes a hand edit, with a 4-place retype.** `UnLocode` (`Regex.IsMatch(code, "^[A-Z]{2}[A-Z2-9]{3}$")` with the literal pattern in the call), `FreightRate.currency` and `ContainerCode` (`Format.IsMatch(value)` on a `static readonly Regex` field) all came out as `Any.String()...` + a non-compiling sentinel, as the docs promise. The TODO comment is excellent (it quotes the pattern and names the retype), but the edit it describes is purely mechanical (`AnyString` -> `AnyPattern` in 4 places) and I did it three times. For the `Regex.IsMatch(x, "literal")` shape, the pattern is right there and inside the supported subset; I expected at least a switch or a clearer reason why the tool does not do it itself. The docs do explain the reason (silent partial translation is worse), so this is by design; it is still the most common cost of this domain.
4. **A tied pair that needs one more rule (`Leg`) forces a rewrite of the whole generated file.** The tool recognised `arrival <= departure` and wrote an `Any.OrderedPair(..., strict: true)` with pin bookkeeping (`_departurePin`, `_arrivalPin`, `DepartureAndArrival()`), then marked all four params `to verify` because of `arrival - departure > MaxTransit` ("ties arrival to departure"). The doc's remedy ("draw a start and a duration") is right, but to apply it I could not just edit `Generate()`: the pair fields and the pin members would have become dead or misleading, so I replaced the file. `--force` would now destroy it; I did not find (in the pages I read) the advice "move your replacement to a neighbouring partial file". I expected the scaffold to be incremental, not all-or-nothing, for this very common shape (start/end + max duration).
5. **`Shipment`: a constraint tying a drawn enum to two other parameters has no documented idiom.** The docs cover two-parameter ties (`OrderedPair`, `Then`, `DifferentFrom`). For "weight and volume must fit the drawn container type" I wrote in `Generate()`: draw the type, then `_grossWeightRecipe.WithKilograms(k => k.LessThanOrEqualTo(type.MaxPayloadKilograms()))` — and, to keep a test's pin working, a `ReferenceEquals(_grossWeight, _grossWeightRecipe)` check (otherwise a pin would be ignored or the recipe override a pin). That `ReferenceEquals` trick is mine, not suggested anywhere; I found no better way to know "has this parameter been pinned?" The docs warn (correctly) that a pin on one side of a tie depends on the seed; this bit me in design: with the container type random, any test that pins a weight > 26 500 kg or a volume > 33.2 m3 must also pin the type, or it fails on some seeds.
6. **`Any.DateTimeOffset()` default range makes `departure + duration` overflow.** I knew from `dates-and-times.en.md` (MinValue..MaxValue) that I had to bound the departure; this is documented and I did bound it (2020..2035), but a scaffolded `Any.DateTimeOffset()` for `departure` is a latent `ArgumentOutOfRangeException` for any user who follows the doc's own advice and adds a duration. Not a bug, but the TODO comment on `departure` does not mention it.
7. **Skipped-with-seed convention vs deterministic defects.** The brief asks for `Skip = "domain defect: ..., seed ..."`. The four defects I found are deterministic on literals (no draw involved), so the seeds in the skip texts are only the seeds of the failing run; they replay nothing. Not a library problem.
8. `[assembly: Reproducible]` works as documented: the failing tests printed `[JustDummies] These arbitrary values were seeded with -688145543. Reproduce this run with [JustDummies.Xunit.Reproducible(Seed = -688145543)].` in "Standard output". The seed line is only printed for failures, so green runs show nothing: good, and I had to rely on that for 12 repeated runs (no way to see which seeds ran, by design).

## What worked well
- The getting-started page is excellent for the mindset: "if an `anyXxx` reaches your assertion it is not a dummy" directly shaped the tests (boundary values, payloads, instants and rates are literals; ids, containers, currencies, locations are dummies).
- `any generate` with several types at once, `--output`, `--entry-point any` and the recap (`guard`, `AnyX`, `to verify`, `unread guards`) are very readable. Weight and Volume came out perfect and even reference the domain constants (`LessThanOrEqualTo(Weight.MaxGrossKilograms)`).
- The `TODO(any)` sentinel approach: my own build told me, at the line, which five generators needed me. The comment text (pattern quoted, retype named) made `UnLocode` a 2-minute edit.
- Instantaneous help from the docs for the check digit: the Luhn-style `.As(body => body + digit)` sample was the exact shape needed for ISO 6346.
- `DifferentFrom` on a scaffolded generator (`_destination.DifferentFrom(origin)`) worked on the first try, as documented.
- Pinning plus defaults composed well: `Any.Shipment().WithContainerType(type).WithVolume(new Volume(x))` reads like the test intent, and the other fields stay arbitrary.
- No analyzer diagnostic ever fired on correct code (0 warnings), so no noise.

## Fluency: 4 / 5
I got to a green suite fast and the library made the dummy/literal decision easy to reason about. Points lost for the first-command stumbles (`dotnet test --project` and `dotnet restore` before `any`, neither explained for a consumer) and because the interesting generators of this domain (`Leg` with a max duration, `Shipment` with type-dependent limits) needed hand-written `Generate()` logic with no documented way to detect pins or to keep the edits out of the `--force` blast radius; I solved both with my own conventions rather than a documented one.
