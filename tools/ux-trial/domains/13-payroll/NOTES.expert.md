## Frictions and surprises, in order
1. **`dotnet test --project Tests.Expert` does not work as given.** On SDK 10.0.114: `MSBUILD : error MSB1001: Unknown switch ... --project`. The fallback `dotnet test Tests.Expert` gives `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later. If you use dotnet test, you should opt-in to the new dotnet test experience`. I had to add `W/global.json` with `{ "test": { "runner": "Microsoft.Testing.Platform" } }`. No page of the docs I read (getting-started, xunit package page) says that a `xunit.v3` test project needs it on .NET 10; a newcomer follows "dotnet test" and meets two unreadable errors.
2. **`any generate` before restore**: `✗ EmployeeId: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. Clear and actionable; I only note the doc's "run it from your test project" does not mention it.
3. **Cross-parameter rules are the real work, and the tool can only point at them.** For `EmploymentContract` four parameters came out `to verify, unread guards` all pointing at `Validate(type, hiredOn, endsOn, weeklyHours);` — the rules (type ↔ end date ↔ weekly hours ceiling ↔ end > start) live in a private `static void Validate`, which the tool does not follow (documented: a `void` helper is "marked as before"). Expected: at least the per-parameter bounds read in that helper (`weeklyHours < 1`, `hiredOn < EarliestHiringDate`). I read `Domain/EmploymentContract.cs` and wrote the base myself. The page "When a guard ties two parameters" gave the right recipe ("derive one draw from another inside `Generate()`") and it worked first time.
4. **Deriving a parameter silently retires its `With…` surface.** After deriving `endsOn` and `period` in `Generate()`, the scaffolded `WithEndsOn(Func<AnyDateOnly,…>)` / `WithPeriod(Func<AnyPayPeriod,…>)` refinements no longer mean anything (a lambda cannot express "after the hiring"). The page warns about the pin; it does not say what to do with the *lambda* overload. I deleted them. And since I edited the scaffolded file (not a partial neighbour), `any generate … --force` will erase it: the page says so, but there is no seam (e.g. a `partial` hook called by `Generate()`) to put the tie in a file that survives.
5. **The scaffolder's own output trips its own analyzer.** `AnyPayslipLine.cs` line 42, `Any.Decimal().Positive().WithScale(2)`, is flagged JD036 (Info) once raised to warning (`dotnet_diagnostic.JD036.severity = warning` in `.editorconfig`): "This floating-point dummy declares no range: one draw in ten spans the whole type". Two things: the message says *floating-point* for a `decimal` chain; and the tool cannot invent a ceiling the constructor does not declare (`amount > 0` and cents only), which is exactly what the domain is missing (finding D2 below). The Info level is invisible in `dotnet build`, as documented.
6. **`WithLabel(null!)` is ambiguous**: `error CS0121: The call is ambiguous between 'AnyPayslipLine.WithLabel(string)' and 'AnyPayslipLine.WithLabel(Func<AnyString, AnyString>)'`. The CLI page documents the cast for nullable parameters; here the parameter is non-nullable and I am testing the null refusal. Fixed with `(string)null!`, and the same for `WithEmployee((EmployeeId)null!)`, `WithRate((HourlyRate)null!)`, `WithLines((IReadOnlyList<PayslipLine>)null!)`. Four casts in a null-refusal suite; acceptable but unexpected.
7. **A prepared generator cannot be passed to `With…`**: `error CS1503: Argument 1: cannot convert from 'AnyEmploymentContract' to 'EmploymentContract'` at `Any.Payslip().WithContract(AnyContractHiredOn(date))`. Documented ("A prepared generator is reused as a lambda") but the compiler message gives no hint; I moved the helper to `AnyEmploymentContract.NotATraineeship()` in a partial file, which reads better anyway.
8. **A calculation slip of mine, caught by a clean failure report**: `Expected: 202.80 / Actual: 101.40` (I had hired the employee 4 years earlier than needed for the 6 % tier). The failure printed `[JustDummies] These arbitrary values were seeded with -1736412450. Reproduce this run with [JustDummies.Xunit.Reproducible(Seed = -1736412450)]` as promised, although the failure was mine and not the draw's.
9. **A drawn value found a real defect.** A test "the net pay of a payslip is not negative" on `Any.Payslip().Generate()` failed in about 2 % of payslips (64/3000, then 12/400 over small seeds, 8/400 over random seeds): `System.OverflowException : Value was either too large or too small for a Decimal.` from `NetPay`/`GrossPay`/`TotalBonuses`. The scaffolded `PayslipLine.amount` is `Positive().WithScale(2)`, whose tenth draw reaches ~7e28, and the domain has no ceiling on a line (see D2). Seed 12 replays it (`[Reproducible(Seed = 12)]` verified). Skipped with the seed.
10. **Seed sweeps are cheap**: I looked for a failing seed with `using (Any.UseSeed(seed)) { … }` in a loop. It worked and is deterministic; but it is not documented as a technique for "find me a seed for this failure" (I found it from the reproducibility vocabulary).

## What worked well
* The TODO sentinels: a build that stops exactly at the three types that need a human, with the rule quoted (`^EMP-\d{6}$`, the `Validate` call, "ties period to contract").
* The regex TODO spells out the four places to retype `AnyString` to `AnyPattern`; I followed it without a compile error.
* `HourlyRate`, `PayPeriod`, `PayslipLine` scaffolded with constants referenced (`PayslipLine.MaximumLabelLength`) and `.WithScale(2)` read from `decimal.Round(...)`: correct, nothing to do.
* The `With…` surface makes refusal tests short and honest: `Any.PayslipLine().WithAmount(0m).Generate()` states one invalid fact and lets everything else be a valid dummy.
* `Any.Payslip().WithContract(c => c.WithWeeklyHours(39).WithRate(…))` keeps the arithmetic's inputs literal and the rest drawn; the period drawn *after* the contract made the "tie" invisible in the tests.
* `[assembly: Reproducible]` + per-case seeds in theories, and a seeded replay that really reproduces.
* The documentation's discipline ("if an `anyXxxx` reaches your assertion it is not a dummy") kept me honest: I removed two tests that were only asserting my own generator.

## Fluency: 4 / 5
Scaffolding plus hand completion was quick and the library's vocabulary (`Between`, `Except`, `WithScale`, `StringMatching`, `.Then`, pins and lambdas) covered every need on first reading. The points lost are the .NET 10 `dotnet test` setup nobody tells you about (1), the cost of a domain whose rules live in a private `Validate` (3-4: the tool is honest but cannot help, and the hand-edited `Generate()` is fragile against `--force`), and a few compile errors whose message does not point to the documented answer (6-7).

## Domain observations (not fixed, `Domain/` untouched)
* D1. `Payslip` copies `lines` without checking elements: a `null` element is accepted and `TotalBonuses` then throws `NullReferenceException` (`AddLine` does refuse null). Test `A_payslip_with_a_null_line_is_refused` is skipped.
* D2. `PayslipLine.Amount` has no ceiling (unlike `HourlyRate`), so `TotalBonuses`/`GrossPay`/`NetPay` throw `OverflowException` for lines summing past `decimal.MaxValue`. Test `The_net_pay_of_a_payslip_is_not_negative` is skipped, seed 12.
* D3. `EmployeeId` accepts `EMP-` + non-ASCII digits and a trailing line feed (`"EMP-123456\n"`); stated in the model, pinned by two characterisation tests, but an identifier with a newline is probably not wanted.
* D4. `HourlyRate` and `PayPeriod` are value objects without value equality (only `EmployeeId` has it). Two equal rates compare unequal.
* D5. A contract may be hired after 2100-12-31 (no upper bound on `HiredOn`), but then no payslip can ever be issued for it (`period` is limited to 2100): `ArgumentException` on every period.
