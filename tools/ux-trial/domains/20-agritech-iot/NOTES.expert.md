## Frictions and surprises, in order
1. **`dotnet test --project Tests.Expert` does not work on the SDK of this machine (10.0.114).** `MSBUILD : error MSB1001: Unknown switch ... Switch: --project`. `dotnet test Tests.Expert` then fails with `Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later ... opt-in to the new dotnet test experience`. I added a `global.json` with `{"test":{"runner":"Microsoft.Testing.Platform"}}` in the domain folder. xunit.v3 forces MTP, so every consumer on .NET 10 hits this; neither the xunit adapter page nor getting-started says a word about it. Expected: the docs list the one-line `global.json` (or the right command) next to "xunit.v3 4.0.2 or later".
2. **`any` needs a restored project and says so well**: `✗ SensorId: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. Fine, noted because it is the first thing a newcomer meets.
3. **`SensorId` scaffold: `Any.String().NotBlank().WithLength(9)`, flagged `to verify, guard, unread guards`.** The guard is `value.Length != 9 || !value.StartsWith(Prefix, Ordinal)` followed by a char loop. The tool read the left branch of the `||` and not the right, and reports "and 1 more". That is honest and the build stops. But the proposed recipe would be refused on essentially every draw, and the comment gives no hint that the `StartsWith(const)` / char-class loop could become `StringMatching`; I had to know to go there (strings page). The retype `AnyString` -> `AnyPattern` is documented to the letter, and a global replace did it in seconds, but it is four coordinated edits for a one-line idea.
4. **`BatteryVoltage` (Half): `Any.Half()  to verify, unread guards`.** The guard `Half.IsNaN(v) || v < Minimum || v > Maximum` compares with `public static readonly` fields, not `const`, so the tool cannot see the bounds; the scaffolded `Any.Half()` spans up to 65 504 and would almost never satisfy the constructor. Reasonable, but the comment could say "these are static readonly, not const" as the cause; I had to infer it. Writing `Between(BatteryVoltage.Minimum, BatteryVoltage.Maximum)` was easy and follows the domain.
5. **`Geofence`: both parameters `to verify`, nothing generated for the tie.** The rule is between `southWest.Latitude` and `northEast.Latitude` (members of the parameters), which the `OrderedPair` automation does not cover (it is for two parameters of one ordered type). Documented, and the docs offer four recipes; none is a copy-paste for "two composed parameters tied through a member". I wrote it in `Generate()` (see What I did). Cost: ~10 lines plus the decision to drop the `WithNorthEast(GeoCoordinate)` pin (otherwise a pin would either be ignored or hold the rule only on some seeds, which the docs warn about). That left the private field `_northEast` assigned and never read, with no compiler warning to remind me. A hand-written `Generate()` that stops reading a field is invisible.
6. **`ReadingBatch` scaffold writes `Any.ListOf(new AnySensorReading()).NonEmpty().WithMaxCount(ReadingBatch.MaximumReadings)`**, i.e. batches of up to 500 000 readings by default, each with six sub-objects. The recap does flag it: `the guard's ceiling of 500000 elements steers every default draw toward that size (ADR-0076); consider a smaller default in AnyValidReadings()`. Two problems: (a) the advice is only in the transient console recap, not in the generated file, so someone who scrolls past it commits a generator that makes every test allocate hundreds of thousands of objects; (b) it cites `ADR-0076`, a maintainers' record a consumer cannot open (the docs I was given contain no `adr/` folder, so links like `../../for-maintainers/adr/...` dangle). I replaced it with `WithCountBetween(1, 20)`.
7. **`SensorReading.takenAt`: `Any.DateTimeOffset()  to verify, unread guards`** for `takenAt.Offset != TimeSpan.Zero`. The docs state that an unconstrained draw keeps `+00:00`, so the recipe was already right and the sentinel only asked me to confirm it. Having to read the dates page to be sure is the right cost for a "to verify", but this exact guard (`Offset != TimeSpan.Zero`) is a very common domain rule and could be read.
8. **Valid bases are private, so a test that needs just a latitude has no clean way to get one.** I wrote 8+ tests that need "a valid longitude, I don't care which" while the thing under test is the latitude. The alternatives are drawing a whole `GeoCoordinate` and taking `.Longitude` (draws an object to use a number, the docs say not to) or restating `Between(-180, 180)` less the endpoint in the test (the invariant duplicated). The docs' own answer is the one-line internal accessor in a partial file; I did that (`AnyGeoCoordinate.Custom.cs`), it works, and the tests then read well (`AnyGeoCoordinate.ValidLongitude().Generate()`). It is the only file I had to write only to avoid duplicating a constraint.
9. **Half-open longitude is awkward to say with literals.** Boundary tests need `179.99999999999997` and `-180.00000000000003`; there is no `Any`-side help and none is needed (they are literals on purpose), just noting that "the largest double below 180" is a recurring need that I wrote by hand. (`Math.BitDecrement` in an `[InlineData]` is not allowed, so the values are spelled out.)
10. **Entry point `--entry-point any` (C# 14 extension members) worked first time** on net10.0 with no language-version setup. `Any.SensorId()`, `Any.Geofence()` read exactly like `Any.Int32()`. No friction here, listed because the docs warn about C# 14 and it was a non-issue on this SDK.
11. **`DifferentFrom` on a scaffolded component, `Any.SensorId().WithValue(value => value.DifferentFrom(anyId.Value))`, works** and reads well because `AnyPattern` offers it, as the docs say. It still redraws internally (bounded); not an issue for an id space of 16^6 + digits.
12. **No analyzer diagnostic fired on 112 test methods**, build had 0 warnings. I could not tell whether that is because I wrote nothing wrong or because Info-level rules (JD030, JD031, JD036) are silent by design; the docs say Info never prints in `dotnet build`. For a heavy user it would help if the docs said how to see them in an IDE-less workflow in one line (`.editorconfig` severity) on the packages page, not only in the individual rule pages.

## What worked well
- The `any` recap table is a real work list: `to verify` rows are exactly the five places where my domain has a rule the library cannot guess, and the build refusing to compile until I read each is the right behaviour. In this domain every one of those flags was legitimate (SensorId format, Half bounds, Geofence tie, UTC offset); none was a false alarm.
- Pinning one part through a lambda: `Any.SensorReading().WithHumidity(h => h.WithPercent(30))` and `.WithPosition(p => p.WithLatitude(x).WithLongitude(y))` keep everything not in the assertion drawn and visibly arbitrary. The tests read as "a reading whose only trait is its humidity". The `ReadingWithHumidity`, `ReadingAt`, `ReadingOf` helpers are one line each.
- The dummy / literal split falls naturally in this domain: sensor ids, positions, battery on a humidity test, humidity on a geofence test are all dummies; every threshold, bound, bit-neighbour and humidity percent in an assertion is a literal that carries the rule. `Any.DateTimeOffset().Between(...).WithOffset(...)` for "a valid instant stamped with a wrong offset" is a perfect fit (and, with an unbounded draw, `ToOffset` could have overflowed, which the docs warn about).
- `[assembly: Reproducible]` plus the printed `[JustDummies.Xunit.Reproducible(Seed = ...)]` line: the failure path is exactly what the docs promise.
- `DifferentFrom` for "two ids that differ", and the `Same`/`Equal`-by-value tests built on draws (`new SensorId(first.Value)` as a second instance) say the equality tests precisely.
- Refusals with `ParamName` assertions were easy because every message is about one named parameter; no library help needed.

## Domain findings recorded
- `RelativeHumidity(double.NaN)` is accepted (documented in MODEL.md as intended). A NaN reading makes `AverageHumidity()` NaN and `ShouldIrrigate` silently false. Skipped test `A_percent_that_is_not_a_number_is_refused`.
- `IrrigationPolicy` rejects `double.NaN` only because its bit pattern has the sign bit set and `ThrowIfNegative` sees "negative"; a NaN with the sign bit clear (`BitConverter.Int64BitsToDouble(0x7FF8000000000000)`) is accepted. Skipped test `A_threshold_that_is_a_positive_signed_NaN_is_refused_like_any_other_NaN`; the `double.NaN` test passes.
- `IrrigationPolicy.ShouldIrrigate(null)` and `ReadingBatch.OutsideOf(null)` throw `NullReferenceException`, not `ArgumentNullException`; `ReadingBatch` accepts a `null` item in its list and fails later in `AverageHumidity()`. Three skipped tests. (MODEL.md says these are not null-checked; I still think they are defects for a public API.)
- None of the above involves a drawn value, so there is no seed to quote; each is reproduced by a literal.

## Fluency: 4 / 5
The library did what it promised and the dummy/literal discipline was easy to keep in this domain; the scaffold was a good first draft where the guards were simple (latitude, longitude, humidity, soil temperature, threshold: all `guard` rows, correct) and an honest stop where they were not. I lose one point for the cost around the edges of the scaffold: the SensorId and Geofence completions were work I needed the docs for (four-line retype, hand-written tie), the 500 000-element default is dangerous if the console recap is missed, the recap cites an ADR a consumer cannot read, and the very first command of a test run (`dotnet test --project`) fails on a .NET 10 SDK without a `global.json` the docs never mention.
