## Frictions and surprises, in order
1. `dotnet test --project Tests.Regular` -> `MSBUILD : error MSB1001: Unknown switch. ... --project Tests.Regular`; `dotnet test Tests.Regular` -> `Microsoft.Testing.Platform.MSBuild.targets(395,5): error : Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later...`. The SDK (10.0.114) only accepts `--project` when `global.json` opts into the Microsoft.Testing.Platform runner; the template csproj and the docs do not mention it. I added `W/global.json` with `{"test":{"runner":"Microsoft.Testing.Platform"}}`. Not the library's fault, but the xunit adapter page should say so since `OutputType Exe` + xunit.v3 is exactly what hits it.
2. `any generate SensorId ...` before restore -> `✗ SensorId: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. Clear and actionable; I would have liked the tool to say it before analysing 8 types (it stops at the first).
3. `SensorId`: the tool read `value.Length != 9` (-> `.WithLength(9)`) and the `NotBlank` helper, but not `StartsWith(Prefix, Ordinal)` nor the `char.IsAsciiHexDigitUpper` loop; it printed `Any.String().NotBlank().WithLength(9)  to verify, guard, unread guards` and a clear sentinel. Expected: nothing more (guards are not regexes). Cost: replacing `AnyString` by `AnyPattern` is the documented 4-place edit (field, ctor param, factory return, Func); the sentinel-deletion left a blank line at the top of the method. Fine, but this "pattern-shaped value object" is common enough that a `--pattern` or an automatic retype would save the sed.
4. `BatteryVoltage(Half)`: guard `volts < Minimum || volts > Maximum` compares with `public static readonly Half` fields, not constants, so the tool gave a bare `Any.Half()` + sentinel. Expected: the same (it only reads constants), but the recipe it falls back to draws the whole Half range (up to 65504), so ~all draws would be refused; I am glad the build stops. Idea: read `static readonly` fields initialised with a constant/cast expression.
5. `Geofence`: both parameters `to verify`, "ties southWest to northEast, and 1 more". The doc's `OrderedPair` section covers a guard comparing two parameters of an ordered type, but this guard compares a *member* (`.Latitude`, `.Longitude`) of two composed values, on two axes. No recipe-level fix exists, so I rewrote `Generate()` to draw two points and take min/max per axis. Consequence (documented in the docs for this situation): `WithSouthWest(...)`/`WithNorthEast(...)` pins no longer mean what they say (the corners are re-derived). In tests I build fences from literals when the fence matters, and use `Any.Geofence()` only for "any fence". It took the longest of everything (~10 min, mostly deciding between sorting, a delta approach, or `Any.Combine`). A documented recipe for "two composed values ordered on members" would help.
6. `ReadingBatch`: the scaffold is `Any.ListOf(new AnySensorReading()).NonEmpty().WithMaxCount(ReadingBatch.MaximumReadings)` with the note `the guard's ceiling of 500000 elements steers every default draw toward that size ... consider a smaller default in AnyValidReadings()`. Good note, but the generated default is dangerous as scaffolded (each element is a 6-object graph); a regular user will not read the recap line and will wonder why the suite is slow. I lowered it to 20. Maybe the tool should lower such a ceiling itself above, say, 1 000.
7. `SensorReading.takenAt`: marked `to verify` on `takenAt.Offset != TimeSpan.Zero` with `Any.DateTimeOffset()`. It is in fact already right (the dates page says the offset stays +00:00 unless you opt in), but you only know that by having read that page. The sentinel text did not hint at it; I deleted the sentinel on the strength of the docs. Idea: let the tool recognise `Offset != TimeSpan.Zero` -> `Any.DateTimeOffset()` with no `to verify` mark.
8. `Half`: `Any.Half().Between(Minimum, Maximum)`, `.LessThan(Minimum)`, `.GreaterThan(Maximum)`, `.GreaterThanOrEqualTo(..).LessThan(..)` all compiled and behaved; `Half.BitDecrement/BitIncrement` made neighbour tests easy. No friction, just noting I checked.
9. Generated files are in namespace `AgriTech.Domain` (the target type's), although they live in the test project (default `--namespace`). It works and makes `Any.SensorId()` visible without a `using`, but a test project declaring types in the production namespace surprised me; I kept the default.
10. NaN/sign-bit trap (domain, not library): `new IrrigationPolicy(double.NaN, 1)` is refused but `new IrrigationPolicy(BitConverter.Int64BitsToDouble(0x7FF8000000000000), 1)` is not. I only found it because MODEL.md says "NaN handling is that of the helpers"; the library's generators never draw NaN (documented), so no draw could have found it. Recorded under domain defects below.
11. Nothing failed on a drawn value in the 13 runs. The draws that mattered (one-sided `Any.Double().GreaterThan(100d)` etc.) occasionally reach huge magnitudes by design (10 % of draws) and every refusal test coped, as expected.

## What worked well
- One `any generate` command for the whole graph, with `AnyX` links wired between types in the right order and the build naming exactly what was left (4 of 8 stopped the build, each with a precise sentinel and line reference).
- The `With…(lambda)` refinement on composed values (`WithPosition(p => p.WithLatitude(l => l.GreaterThan(30d)))`) made "a point north of the fence" a one-liner without losing the base's validity.
- `Any.Half()` and `Any.Single()` bounds (`Between`, `LessThan`, `GreaterThanOrEqualTo`) with `Half` constants just worked; one-sided double draws made the out-of-range refusal tests honest (any value beyond the bound, not one literal).
- `Any.StringMatching` handles groups/alternation, which gave me "non-hex character at any of six positions" in one pattern.
- `[assembly: Reproducible]` in a 3-line file: whole suite replayable, 12 re-runs silent.
- The refinement/sentinel documentation matched what I got, including the `AnyString` -> `AnyPattern` edit list.

## Fluency: 4 / 5
Everything the day-to-day flow promises (scaffold, complete, test, repeat) worked and the suite was green from the first run with 180 cases and no flakiness over 13 runs. The points off are the two spots where I was on my own: the two-axis tie between composed values (Geofence), which had no documented recipe and silently changes the meaning of the generated pins, and the scaffolded 500 000-element default, plus the unrelated but time-costly `dotnet test --project` / MTP setup that neither template nor docs mention.

## Domain defects found (tests kept, marked Skip)
- `RelativeHumidity(double.NaN)` is accepted (no exception); one NaN reading makes `ReadingBatch.AverageHumidity()` NaN and `ShouldIrrigate` silently false. Test: `RelativeHumidityTests.A_percentage_that_is_not_a_number_is_refused`.
- `IrrigationPolicy` accepts a NaN threshold with the sign bit clear (`0x7FF8...`), refuses `double.NaN` (sign bit set) by accident of `ThrowIfNegative`. Test: `IrrigationPolicyTests.A_threshold_that_is_not_a_number_is_refused_whatever_its_sign_bit`. Such a policy never irrigates.
- `IrrigationPolicy.ShouldIrrigate(null)` and `ReadingBatch.OutsideOf(null)` throw `NullReferenceException` instead of `ArgumentNullException`. Tests skipped accordingly. (Also: null items inside the readings list are not rejected by `ReadingBatch`; not tested.)
