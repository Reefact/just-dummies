  - `AnyGasSchedule`: each base cost `Between(21 000, 29 000 000)` (credits) / `Between(21 000, 30 000 000)` (approve, burn), which makes `max(...) + surcharge <= 30 000 000` true by construction. The scaffolder's own `OrderedPair` for `transfer <= transferFrom` was kept.
  - `AnyTransactionEnvelope`, `AnyReceipt`: gas price bounded to `2^256 / 30 000 000` so `gas x price` always fits; sender non-zero comes from the address generator.
  - `AnyTokenDefinition`: rewritten by hand (cap is a whole number of tokens, i.e. tied to `decimals`): draws `decimals`, then a count of whole tokens, builds the cap; `WithSupplyCap` / `WithWholeTokens` / `WithDecimals` pins.
  - `AnyLedger`: rewritten by hand (initial supply and minimum gas price are tied to the cap and the schedule): token and schedule are drawn first, the two amounts after, inside `Generate()`.
  - `AnyTransferRecord`, `AnyAccount`: only the TODO lines removed.
- Tests (`Tests/`, 303 methods, 31 of them theories, 425 executed cases, 4 skipped): `AddressTests`, `TokenAmountTests`, `ExactDecimalTests`, `TokenDefinitionTests`, `TokenPriceTests`, `GasScheduleTests`, `TransactionEnvelopeTests`, `ReceiptTests`, `TransferRecordTests`, `AccountTests`, `LedgerRefusedExceptionTests`, then the aggregate: `LedgerConstructionTests`, `LedgerQueryTests`, `LedgerTransferTests`, `LedgerFeeTests`, `LedgerNonceAndDeadlineTests` (nonces, deadline inclusive, and the order of the checks pair by pair), `LedgerAllowanceTests` (approve / increase / decrease / transferFrom / unlimited allowance), `LedgerMintAndBurnTests`, `LedgerScenarioTests` (sum of balances = supply after a mix, receipts order, max supply moved without wrap). ## Frictions and surprises, in order
1. **`dotnet test --project Tests.Regular` is refused without a `global.json`.** Command: `dotnet test --project .` -> `MSBUILD : error MSB1001: Unknown switch ... Switch: --project`. xunit.v3 test projects are Microsoft.Testing.Platform executables and .NET 10 only accepts `--project` when `global.json` says `"test": { "runner": "Microsoft.Testing.Platform" }`. Neither the xunit package page nor getting-started mentions it (the PROJECT-README only says the repo pins its SDK in `global.json`). Expected: a line in the xunit adapter page. I added a `global.json` at the workspace root.
2. **`any generate` before `dotnet restore`**: `✗ Address: this project has not been restored, so its package references cannot be read. Restore it, then run the command again: dotnet restore`. Clear message, one run lost; the CLI page says "Requires the JustDummies package" but not "restored".
3. **`BigInteger` has no generator, and the recap does not say so.** `TokenAmount(BigInteger)` and `ExactDecimal(BigInteger, int)` come out as `baseUnits  BigInteger  new AnyBigInteger()  to verify, AnyX, unread guards` / `mantissa  BigInteger  new AnyBigInteger()  AnyX`: the `AnyX` column reads as "drawn through the generator that type owns", and the build then fails with CS0246 on `AnyBigInteger` (documented as the work list for *my* aggregates, but `BigInteger` is a framework struct: `any generate BigInteger --dry-run` proposes a nonsense scaffold of `BigInteger(ReadOnlySpan<byte>, bool, bool)` with `value  ReadOnlySpan<byte>  —  TODO, no source`). `Any.BigInteger()` does not exist in the generator reference either. I hand-wrote `AnyBigInteger` (60 lines: uniform draw over `Between`, built from `Any.UInt64()` words) so the scaffolded files compile untouched. For any finance / crypto domain this is the first wall.
4. **Regex guards cost four edits per parameter.** `Address`, `TokenPrice.quoteCurrency`, `TokenDefinition.symbol` are all `^...$` regexes in the domain, so each is `to verify, unread guards` with the retype instructions (`AnyString` -> `AnyPattern` on the factory, the recipe field, the recipe constructor, the `Func`). Followed as written it works, but it is mechanical and I did it with `sed`; my first sed mangled `Func<AnyPattern, AnyString>` and cost a compile round. Expected (and the docs say it is deliberate) no translation of the pattern; a `--regex` helper or generating the `AnyPattern` retype ready for the user would remove the chore.
5. **Ties that the tool cannot honour make the generated `Generate()` wrong, and re-running `--force` would erase the fix.** `TokenDefinition` (cap must be a multiple of `10^decimals`) and `Ledger` (initial supply <= cap, `minimumGasPrice x transfer <= cap`) report `ties initialSupply to token, and 1 more` per parameter: accurate and helpful. The remedy in the docs (derive inside `Generate()`) is right, but it means rewriting the generated file from the constructor up (about 150 lines each), after which the generator is no longer scaffolder-owned. The partial-class escape does not cover this (the fields and constructor are generated). Expected: some way to keep `Generate()` custom without giving up the rest of the file.
6. **A generator cannot be passed to `With…`.** I wrote `Any.Ledger().WithToken(TokenCappedAt(1_000))` with `TokenCappedAt` returning an `AnyTokenDefinition` and got `CS1503: Argument 1: cannot convert from 'AnyTokenDefinition' to 'TokenDefinition'`. Documented ("A prepared generator is reused as a lambda") and I had read it, but writing the helper first as a generator is the natural first move; the helper became `Func<AnyTokenDefinition, AnyTokenDefinition>`. The CS1503 text gives no hint toward the lambda form.
7. **`LedgerRefusedException(RefusalReason, string)`: noise in the recap.** `message  string  Any.String()  to verify, unread guards` with `unread guard at LedgerRefusedException.cs, line 7: message`: that line is `: base(message)`, there is no guard. Harmless; I did not need that generator (the exception is built with `Any.Enum<RefusalReason>()` and a string directly), I deleted it.
8. **The "work list" is long when everything is scaffolded at once.** Nine value objects and three entities at once produced 8 files that "will not compile" with TODO sentinels in every one; each `to verify` row needs reading the constructor again. This was fine with the recap and the `TODO(any)` line quoting the guard and its line number, but I had no way to see only the rows that still required work after my first edits (the build lists CS0103 sentinels one by one, per file). A summary command (`any status`) would help.
9. **My own mistakes with literals, not draws** (kept here because they cost reruns): `TransactionKind` has a member with value 0 (`Transfer`) so `(TransactionKind)0` is defined; a gas limit of 50 000 cannot cover a transfer to a new holder (55 000); a default gas limit of 30 000 000 times a non-zero price is a maximum fee no balance covers. None was the library's.
10. **Build output shows no analyzer feedback on the finished generators**: expected (nothing to say), but I only trusted it after planting `Any.String().WithLength(3).StartingWith("ORD-")` once and seeing JD015 appear as a warning. Info-level rules (JD030) do not show in `dotnet build`, as documented.
11. **Seed reporting works but is easy to miss in MTP output**: on failure the line `[JustDummies] These arbitrary values were seeded with 873835480. Reproduce this run with [JustDummies.Xunit.Reproducible(Seed = 873835480)].` is printed under "Standard output" after the stack trace. Fine; I just had to look for it.

## What worked well
- The scaffolder's `guard` / `ties` reporting is accurate: `GasSchedule` got its `transfer <= transferFrom` order through `Any.OrderedPair` with no work, the three-way `gasPrice x gasLimit` tie was named on both parameters, and every constant (`GasSchedule.IntrinsicGas`, `TokenDefinition.MaxNameLength`) was referenced by name rather than copied.
- `--entry-point any` gives `Any.TokenDefinition()`, `Any.Ledger()` etc., so arrange blocks read like the primitives.
- Refining with lambdas (`WithToken(t => t.WithWholeTokens(...))`, `WithBaseUnits(b => b.Between(...))`) composes nicely over a hand-written base: one place states "a token roomy enough", every test reuses it.
- `[assembly: Reproducible]` is one line and keeps the 300 tests honest about their draws; seeds changed every run.
- The failure of a test was never in doubt about "who is wrong": with pins the generators fail on first run when a test breaks a rule (`Any.Receipt().WithKind((TransactionKind)99)` throws the domain's own exception).
- The domain-side findings are all deterministic and a literal reproduces them; the 4 skipped tests are on the one real defect found.

## Domain observations (not library)
- **`$` without `RegexOptions.Multiline` accepts a trailing line feed** in `Address` (a value with `"\n"` in `Value`), `ExactDecimal.Parse("12.5\n")`, the `TokenDefinition` symbol (`"ABC\n"`) and the `TokenPrice` currency (`"EUR\n"`). The four tests are kept and skipped: `Skip = "domain defect: ... trailing line feed ..."` (deterministic, no seed needed, a literal triggers it). `Address.Parse` is not affected (it trims).
- `NonceExhausted` is unreachable through the public API (it needs 2^128 accepted transactions from one sender), so it is untested; there is no way to start an account at a high nonce.

## Fluency: 4 / 5
The documented workflow (scaffold, read the recap, complete the TODOs, refine with lambdas, `[Reproducible]`) held up for a domain with 11 types and a big aggregate, and the diagnostics pointed at the right line each time. Points off for the `BigInteger` wall (a missing generator that the scaffolder presents as if it were there), the missing `global.json` hint for `dotnet test --project`, and the fact that the two most interesting generators (token definition, ledger) end up fully hand-written because the tool correctly detects ties it cannot honour and then leaves nothing of the generated file worth keeping.
